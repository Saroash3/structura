# Structura: A Verified Data Structure Explainer

## 2. Abstract

Structura answers a question about a data structure or an algorithm with a short animated lesson. It narrates the lesson aloud, ends with a quiz, and can export the lesson as an MP4 video. The supported topics are arrays (including 2D, static, dynamic and jagged arrays), stacks, queues, linked lists, binary search trees, BFS and DFS on graphs, bubble sort and insertion sort.

A large language model (Gemini) analyses the question and plans the lesson as a list of operations, such as "enqueue 40". It never draws or states the data itself. Real data structures written in Python run every operation and record the true state after each step. A verifier then checks every number and claim in the narration against those states. Sentences that fail are repaired once by the LLM; if they still fail, a sentence generated by code from the true state replaces them.

A coverage gate checks that the lesson actually answers the question that was asked. If it cannot, the user gets an honest notice instead of a wrong lesson.

The voice (Piper), the verification, the quiz, the animation and the video export all run locally. Only planning, narration writing and one judging step use the Gemini API, with at most three calls for each new lesson.

## 3. Introduction and goals

The course handout asks for a tool that explains data structures with a narrated animation, lets the learner revise the video, quizzes the learner, and exports a video.

We read the task as follows. A learner types any question, for example "how does a queue work", "stack vs queue" or "insert 5, 3, 8 into a BST". The system must:

- answer that exact question, not a general summary of the topic;
- show each step on an animated picture of the structure;
- speak and caption a plain-English explanation;
- let the learner slow down or reword one step;
- ask a short quiz about what was shown;
- export the lesson as a video file.

One rule shaped every design decision: a wrong video is worse than no video. A learner cannot tell that an animation shows the wrong queue order or that a sentence states a false count. A confident, polished, wrong lesson does real harm. So every state on screen is computed by real code, and every sentence is checked. A lesson that cannot be made correct and on-topic is refused with an honest message.

Two more rules were added during development:

- The answer to the user's exact question comes first; animation exists only to support it.
- Every explanation must be understandable to a total beginner who has never programmed.

## 4. System overview and architecture

### Pipeline in plain words

1. **Question shape.** The user types a question in the web app. The backend first classifies its shape (list, compare, why, how, complexity, definition, when-to-use, misconception, multi-part, user data, or vague). A vague question such as "help" gets one short clarifying question and no lesson.
2. **Analysis and plan.** One Gemini call returns an analysis and a plan in JSON:
   - the question restated;
   - 3 to 6 answer requirements, each with the kind of evidence it needs;
   - key terms and jargon;
   - answer points;
   - scenes, each with a list of operations and a draft narration.
3. **Normalisation in code.** Invalid operations are removed. Scenes that teach no requirement are dropped. Missing evidence is built from real operations. Algorithm runs are completed. List and compare questions are rebuilt into fixed answer shapes.
4. **Simulation.** The operations run on real data structures, which record the true state after every step.
5. **Verification.** The verifier checks every scene's narration against those states. All failing scenes go back to Gemini in one batched repair call. A scene that still fails gets a sentence generated by code.
6. **Coverage gate.** Code checks that every requirement has a scene, that the question's key terms are said, and that the shape-specific checks pass. Then one judge call (Gemini, temperature 0) checks whether the lesson answers the question and proposes fixes. Fixes are only accepted if they verify. If the lesson still fails, the user gets an honest notice.
7. **Voice.** Piper speaks each scene locally. The audio length sets the scene length.
8. **Quiz.** The quiz is built from the lesson's own data. The answers are computed by running the real structure.
9. **Playback.** The browser plays the lesson. The learner can revise one scene, take the quiz, and download the MP4. The video is built locally with headless Chromium and ffmpeg.

## 5. Core modules

### 5.1 Lesson planner

**What it does.** Turns a free-text question into a lesson plan made only of operations, organised around what the answer must contain.

**How it works.**

- **Question shape.** `answer.question_shape` classifies the question from its wording, for example "types of" means list and "vs" means compare. The analysis call also returns a shape. Code keeps its own reading for the forms it recognises reliably (list, compare, misconception, user data).
- **Analysis call.** `answer.analyze_and_plan` sends one prompt to Gemini with a JSON schema. The answer contains:
  - the subject structure;
  - 3 to 6 requirements, each with an evidence type (trace, count, table, compare, state or none);
  - key terms and jargon with plain definitions;
  - list items, compare sides, a premise verdict and parts, depending on the shape;
  - answer points (one per requirement) and scenes (one point each).
- **Normalisation in code** (`answer.build_plan`):
  - impossible operations are cut;
  - scenes that teach no requirement are rejected (except a short intro and recap);
  - a requirement with no evidence gets a scene built from real operations;
  - sorting and graph runs are completed;
  - a scene may run on another structure only if its requirement names that structure.
- **Fixed answer shapes for some questions:**
  - list questions get one scene per item from the known kinds in `concepts.VARIANTS`, the count when asked, and a recap that names every item;
  - comparisons of two supported structures run the same values and steps on both sides, then a verdict.
- **Schema validation.** Plans are validated with Pydantic models in `planner.py` (allowed structures, allowed operations per structure, roles), then dry-run on the real structures.
- **LLM resilience** (`llm.py`):
  - models are tried in order from `GEMINI_MODELS`;
  - overload, rate-limit, timeout and network errors move to the next model, with exponential backoff (1, 2, 4 seconds and so on, capped at 30 seconds) for up to 5 passes;
  - each call has a 45 second timeout;
  - at most 2 calls run at once;
  - responses are cached on disk by prompt hash, so a repeated prompt costs nothing.
- **If the analysis is unusable**, the same response feeds the older focus pipeline (`planner.make_plan`), but only for shapes it can answer, and only if the lesson mentions the question's key words.

**Key files:** backend/answer.py, backend/planner.py, backend/focus.py, backend/llm.py, backend/concepts.py.

**Example.** For "how many types of array there are", the plan has five requirements, one per kind (1D, 2D, static, dynamic, jagged). Each kind has a picture scene, and three kinds also get a behaviour scene:

- 2D array: reading row 1, column 2;
- static array: refusing a value when full;
- dynamic array: moving to a block twice as big and copying 4 values.

### 5.2 Animation renderer

**What it does.** Draws the true state of each step and animates the change between steps.

**How it works.**

- **Stage views.** `frontend/components/stage.tsx` has one view per structure:
  - array, with index labels, shift highlights and the linear-search scan;
  - 2D array as a grid with row and column labels;
  - static or dynamic array with free slots, a "no room" mark for a refused value, and a note when the array moved to more slots;
  - jagged array, as rows of different lengths;
  - stack, with the top marked;
  - queue, with front and back marked and the circular, priority and deque variants;
  - linked list, with head, tail, current and the rewired pointer highlighted, plus the doubly and circular variants;
  - binary search tree as SVG, with the root, the search path and highlighted leaves;
  - BFS and DFS graphs, with the queue or stack and a visited list;
  - bubble and insertion sort bars, with pass counts;
  - growth tables for complexity lessons.
- **Animation.** Motion (`motion/react`) animates the changes.
- **Player.** `frontend/components/player.tsx` plays one audio file per scene. The step shown on stage comes from the audio clock (`frameAt`): the "before" state while the sentence starts, then the steps spread evenly over the scene. Picture and voice therefore stay in step at 0.5x, 1x and 1.5x, and with per-scene speeds from revisions.
- **Captions and chips.** The caption shows the narration, with a small tag for the running analogy (for example "like a line of people"). When a scene names a part ("leaf", "root"), the stage highlights that part (`scene.named`).

**Key files:** frontend/components/stage.tsx, frontend/components/player.tsx, frontend/lib/types.ts.

**Example.** In the binary search tree lesson, the scene "A value with nothing below it on the road is called a leaf, like 10 here" shows LEAF labels under the leaf nodes.

### 5.3 Step verifier

**What it does.** Makes sure that nothing false is said or shown, and that the lesson answers the question.

**How it works.**

- **Real structures.** `structures.py` implements every structure for real. Each operation returns the true state, and impossible operations (pop on an empty stack, a walk that skips a node) raise an error. Counting functions run the real algorithms to record comparisons, passes, visits and checks. The growth table counts real work for n = 4, 8, 16 and 100.
- **Fact checks** (`verifier.check_scene`):
  - every number in the narration must appear in the true state;
  - claims such as "the front is 20", "Queue is now [C, D]", "20 now points to 40, so 30 is skipped", "the list is sorted" or "O(n)" are checked against the state or the counted run;
  - number words are converted to digits first, so "twenty one" cannot slip past;
  - a rejected claim ("O(1), not O(n)") is not treated as a claim.
- **Specificity.** A scene with operations must name its key facts (for example the value dequeued and the new front), so vague lines fail.
- **Clarity gate** (beginner mode, `clarity.py`):
  - at most 2 sentences per scene with operations, and at most 25 words per sentence;
  - every hard term explained in plain words before or where it is first used, never with another unexplained term;
  - no FIFO or LIFO before the demo;
  - no filler or marketing words, no word repeated back to back, no 5-word phrase said twice;
  - the running analogy in at least 70% of demo scenes;
  - a named part (root, leaf, head, tail) must be visible in that scene's picture.
- **Repair loop.** All failing scenes are sent to Gemini in one batched repair call, with each scene's true state and the exact problems. A scene that still fails gets a template sentence written from the true state; templates are asserted to pass the checks.
- **Coverage gate** ("Answers your question"):
  - deterministic checks: every requirement has a covering scene, the key terms are said, and the shape checks pass (a list names every item in its own scene and the recap restates them, a comparison names both sides and gives a "use X when" verdict, a wrong premise is answered plainly first);
  - one judge call checks coverage and clarity and proposes fixes, which are accepted only if they verify;
  - a safety net built by code adds missing verdicts, premise answers or key-term sentences;
  - if the lesson still does not answer the question, the API returns a `not_answered` notice.
- **Two chips in the player.** "Answers your question" appears only when the gate passed. "Verified" means the facts are true.

**Key files:** backend/structures.py, backend/verifier.py, backend/clarity.py, backend/answer.py (gate and shape problems), backend/lesson.py (`answer_gate`).

**Example.** A wrong sentence such as "We dequeue 99" fails with the error "The number 99 does not appear in the true state", and it is never shipped.

### 5.4 Narration and voice

**What it does.** Writes and speaks the explanation in plain English for a beginner.

**How it works.**

- **Style guide.** The beginner style guide (`answer.style_guide`) goes into the planning, repair and judge prompts:
  - one idea per scene;
  - picture first, name second ("A new person, 40, joins the back of the line, and we call this enqueue");
  - one running analogy per structure;
  - problem before fix for "why" questions;
  - no filler words.
- **Analogies.** Each structure has a fixed analogy in `concepts.ANALOGY`:
  - stack: a pile of plates;
  - queue: a line of people;
  - linked list: a treasure hunt of boxes with notes;
  - array: a row of numbered lockers;
  - binary search tree: forks in a road;
  - BFS: a map of places and roads.
- **Glossary.** `concepts.PLAIN` holds plain-word definitions. For example, a pointer is "a note on each box that says where the next box is". This text contains no numbers or number words, because any number in narration must be a fact.
- **Templates.** `plain.py` holds code-written templates in the analogy's words.
- **Voice.** `tts.py` runs the local Piper voice `en_US-lessac-medium`. Each scene gets its own WAV file, cached in `backend/audio_cache/` by a hash of the text. Arrows such as "head -> 10 -> null" are spoken as "then", and maths such as "O(n²)" is read in words.

**Key files:** backend/answer.py, backend/concepts.py, backend/plain.py, backend/clarity.py, backend/tts.py.

**Example.** "The person at the front, 10, leaves the line, and we call this dequeue. 10 arrived first, so 10 leaves first, and 20 is now at the front."

### 5.5 Quiz generator

**What it does.** Asks three questions about the lesson the learner just watched.

**How it works.**

- Questions are built from the lesson's own values and operations, run on a fresh real structure, so the correct answer is computed by code.
- Distractors are computed too, for example the deleted node or a wrong visit order. Silly options were replaced with plausible mistakes; for example "it goes to whichever side has fewer values" replaced "it is put at the end of a list".
- List lessons ask which kind matches a plain description, and how many kinds were shown.
- Complexity lessons ask counted questions, such as the worst-case count for 5 items.
- For new lessons the wording is also produced by code (no LLM call). The older path could ask Gemini to reword a question, but rejected any rewording that changed a number or label.

**Key files:** backend/quiz.py, frontend/components/quiz.tsx.

**Example.** "In the lesson's tree the root is 50. Inserting 70, which way does it go from the root?" The answer "right" is computed by inserting into a real binary search tree.

### 5.6 Revision control

**What it does.** Lets the learner change one step: "slow down step 4", "speed up", "normal speed", or a content change such as "explain step 2 in simpler words for a beginner".

**How it works.**

- A speed revision changes only that scene's speed.
- A content revision asks Gemini to rewrite only that scene, with:
  - its true state and the facts it must keep;
  - the analogy and the plain glossary;
  - a limit of 2 sentences of 20 words.
- The candidate is checked by the verifier and the clarity gate before it is used, including any problem it would cause in other scenes.
- If it fails or is almost the same as before (similarity above 0.9), Gemini is asked once more at a higher temperature, with the reasons.
- If it still fails, the app says honestly "I couldn't make this step simpler, try describing what confused you" and changes nothing.
- Every other scene comes back byte-identical, and only the changed scene gets new audio.
- The UI shows the scene's text before and after.

This fixed a real bug. A revision once reported "rewritten and re-verified" while the text was identical, because both rewrites failed verification and the template fallback put back the old sentence.

**Key files:** backend/revision.py, frontend/components/generator.tsx.

**Example (measured).** A "simpler for a beginner" revision of step 2 of the binary search tree lesson changed a 7.2 second sentence into a new 4.5 second sentence: "We start by placing 50 as the very first stop on the road, which is called a node." The operations and true state stayed the same, and the other 6 scenes were byte-identical.

### 5.7 Video export

**What it does.** Builds a real MP4 of the lesson on the user's computer, with no external video service.

**How it works.**

- **Render page.** The frontend's /render page draws the lesson at 1280x720 as a pure function of the video time, using the same stage views and timing as the player. It lists its keyframes: each new scene, each step and the quiz slide.
- **Capture.** Python Playwright opens up to 4 headless Chromium pages that capture ranges of keyframes in parallel. Each keyframe gets one frame, plus about 12 frames per second only during the short animation after it. A still picture held for 8 seconds therefore costs a single frame.
- **Voice track.** The scene WAVs are joined so that each scene lasts exactly its duration divided by its speed. The quiz slide is silence.
- **Encoding.** ffmpeg's concat demuxer holds each frame for its exact duration, then encodes H.264 (veryfast, yuv420p, 25 fps) and AAC.
- **Check.** ffprobe confirms video and audio streams, 1280x720, and video, audio and expected durations within 0.5 seconds.
- **The final slide** lists every quiz question with its verified answer.
- **Background and cache.** The export starts in the background a few seconds after a lesson appears. A Download click joins the running job, and a Cancel button stops it. Videos are cached by lesson id plus a hash of everything drawn or spoken, so a revision triggers a new export.

**Key files:** backend/video.py, frontend/components/render-view.tsx, frontend/components/video-export.tsx, frontend/lib/video-api.ts.

**Example (measured).**

- The first version recorded the page in real time: a 57.1 second video took 67.7 seconds to export.
- The current version exported an 81.3 second "types of array" video in 8.3 seconds.
- A repeat download came from the cache in 0.05 seconds.

### 5.8 Web app

**What it does.** Gives each learner an account, a lesson generator, a dashboard and saved lessons.

**How it works.**

- **Stack.** Next.js 16 (Turbopack) with Tailwind and shadcn components.
- **Auth.** Auth.js v5 with email and password (Credentials provider, JWT sessions). Passwords are hashed with bcryptjs (cost 12). Failed logins are rate-limited to 5 per email per 15 minutes, held in memory.
- **Data.** MongoDB Atlas through Mongoose stores users, lessons and quiz results. All database access goes through `lib/data.ts`, where every query is scoped to the signed-in user's id.
- **Pages:**
  - `/app` is the generator, which auto-saves lessons;
  - `/dashboard` shows stats, saved lessons (search, pin, rename, delete) and quiz history;
  - `/lesson/[id]` replays a saved lesson without regenerating it;
  - `/profile` changes name, default level and password, or deletes the account.
- **Route protection.** `proxy.ts` protects routes, and each page re-checks the session on the server.

**Key files:** frontend/app/, frontend/lib/data.ts, frontend/lib/db.ts, frontend/lib/models.ts, frontend/auth.ts, frontend/proxy.ts.

**Example.** After a lesson is generated in /app it appears on the dashboard, and opening it later replays the stored snapshot instantly.

## 6. Setup and technical details

### Requirements

- Python 3.10 to 3.14. The project uses a 3.14 virtual environment in backend/.venv; 3.15 lacked some wheels.
- Node.js 20 or newer, and Git Bash on Windows.
- ffmpeg with ffprobe on PATH, for video export only.
- Playwright's Chromium, installed by `playwright install chromium`, for video export only.
- The Piper voice model `en_US-lessac-medium`, downloaded into backend/voices/ by setup.sh.
- A Gemini API key, and a MongoDB connection string for accounts.

### Setup steps

1. Run `bash setup.sh` from the project root. It:
   - creates backend/.venv and installs backend/requirements.txt (FastAPI, Uvicorn, Pydantic, python-dotenv, google-genai, piper-tts, pytest, httpx, playwright);
   - copies backend/.env.example to backend/.env if missing;
   - downloads the Piper voice;
   - installs Chromium for Playwright;
   - checks for ffmpeg and prints an install command if it is missing;
   - runs npm install in frontend/.
2. If ffmpeg is missing on Windows, install it with `winget install Gyan.FFmpeg` (macOS: brew; Linux: apt).
3. Put the secrets in the two gitignored files:
   - `backend/.env`: GEMINI_API_KEY, GEMINI_MODELS (comma-separated fallback list), GEMINI_MODEL;
   - `frontend/.env.local`: MONGODB_URI, AUTH_SECRET, and the optional NEXT_PUBLIC_API_URL.

   Placeholder versions are in the matching .env.example files. FFMPEG_DIR can optionally point to an ffmpeg folder.
4. Start the backend: `cd backend`, then `.venv/Scripts/uvicorn main:app`. It listens on http://localhost:8000. On Windows, `--reload` can hang.
5. Start the frontend: `cd frontend`, then `npm run dev`. On our machine it runs on port 3001, because port 3000 is taken.
6. Run the backend tests with `cd backend` and `.venv/Scripts/python -m pytest -q`. The end-to-end export test runs only when ffmpeg, Chromium and the frontend are available; otherwise it is skipped.
7. Run the frontend checks with `npx tsc --noEmit` and `npm run lint` in frontend/.
8. Live evaluation: `.venv/Scripts/python eval_lessons.py --shapes`, `--clarity`, `--questions` or `--before-after`. These call Gemini and Piper.

## 7. Evaluation and results

### Automated tests

The backend has 256 pytest tests in 17 test files, and all 256 pass. The most recent full run took 4.4 seconds; the end-to-end export test used a cached video in that run.

Most tests run offline with a deliberately weak fake LLM. It returns placeholder narration, a repair that fixes nothing, and requirements without list items or verdicts. The code alone must then produce a correct lesson.

The tests cover:

- every structure and its impossible operations;
- the verifier, including wrong numbers, number words, false "sorted" claims and pointer claims;
- plan validation, LLM retry and fallback;
- the quiz answers;
- the revision rules, including byte-identical other scenes and the honest "couldn't simplify" message;
- the clarity rules on golden lessons;
- complexity counts;
- 12 varied questions in `test_question_driven.py`;
- 15 question shapes in `test_question_shapes.py`;
- video export: unit tests, ffmpeg tests, and an end-to-end export that requires an MP4 with audio, at least 30 seconds long and exported in under 60% of its duration.

The frontend type check and lint pass.

### Question types tested

List ("types of"), compare ("X vs Y"), why, when-to-use, misconception ("is array access O(n)?"), definition ("what is a vector"), user data (BST inserts, a user's graph), multi-part, how-to, complexity, unsupported topic and vague question.

### What fails or is weak

- One clarity case fails ("what is array"). The answer-first rule keeps a judge rewrite that is correct but not perfectly clear.
- Some LLM sentences in comparisons are stilted, for example "A row of lockers numbered from 0, so you can walk straight to any locker, places 45 at slot 1."
- A "why" lesson can include a weakly related demo step (a lookup).
- The 30-second minimum is not enforced on every lesson: one measured lesson was 25.8 seconds.
- The judge sees the lesson before repairs, to keep the budget at 3 calls; repairs are checked only by the deterministic gate.
- Template fallbacks can repeat a second sentence across similar scenes.

## 8. Critical Analysis

### 8.1 Problem Statement

Learners now ask general AI chatbots to explain data structures. The answers are fluent but generic, and sometimes wrong in ways a beginner cannot see: a wrong pop order, a false comparison count, or a "linked list" drawn as an array.

Tools that generate explainer videos make this worse, because a polished animation looks authoritative. None of them check that the state on screen is the true state.

The standard solution is to prompt an LLM to write a script and then animate it. This does not solve the problem:

- the LLM can hallucinate steps;
- it can drift from the question to a generic overview;
- nothing guarantees that the drawn state, the narrated numbers and the actual operation agree.

We saw this ourselves. Before the coverage gate blocked it on every path, "how many types of array there are" produced a fully "verified" lesson about what an array is, which never named a single type.

### 8.2 Complexity Drivers

- **Correctness versus flexibility.** Free LLM planning can handle any question but cannot be trusted with facts. Fixed code is correct but rigid. We needed both: the LLM plans only operations, and code computes every state and checks every sentence.
- **Beginner simplicity versus accuracy.** Simple sentences can drift from the truth. A garbled sentence passed fact checking: "add 15 between 10 and 20 in memory, which means the computer storage space for data". Every number in it was true, but it was unreadable. Fact checks alone were not enough, so a separate clarity gate was needed.
- **No obvious solution.** The LLM must not draw freely, yet it must handle any question. Each question shape needs a different answer form: a list must name every item, a comparison needs both sides and a verdict, a wrong premise needs a plain "no". The first coverage design silently fell back to a generic lesson when the analysis call said "unsupported".
- **Interacting components.** The planner, verifier, renderer, voice, quiz, revision and export depend on each other.
  - Narration length sets audio length, which sets scene timing in the player and in the video.
  - A revision changes one scene, which changes the cache key of the exported video.
  - A bug in one place showed up in another: a revision reported "rewritten" because the verifier's template fallback restored the old text.
- **Speed versus verification and local voice.** Verification and Piper add time, and each LLM call adds seconds, so we limited new lessons to 3 calls.
- **Narration timing versus animation.** Steps are spread across the audio of a scene, so long sentences slow the animation. That is one reason scenes are capped at 2 sentences.
- **Unreliable free LLM API.** Gemini sometimes returned overload (503) or rate-limit errors. Some model names returned 404 for our key. This required model fallback, backoff, timeouts and a response cache.
- **Local hardware limits.** Real-time video capture took longer than the video itself: 67.7 seconds for a 57.1 second video, and the user once saw 95 seconds for 58. Keyframe capture with parallel pages reduced this to about 8 seconds.

### 8.3 Design Justification

**Alternatives that we tried and replaced:**

- **A fixed list of intents with a topic catalogue (the "focus pipeline").** Our first planner classified questions into a fixed set of intents (what_is, how_op, compare, trace, why, complexity) with prepared sentences per focus. It worked for the questions we expected but failed for others. "How many types of array" became a generic "what is an array" lesson. We replaced it with the question-driven pipeline, where the LLM lists the requirements of the specific question and code validates them. The old pipeline is now only a fallback, restricted to the shapes it can answer.
- **Real-time browser capture for export.** The first exporter played the lesson in headless Chromium and recorded it with Playwright's video recorder, then cut it at the first frame with ffmpeg. It was correct but slower than real time. We replaced it with deterministic keyframe capture in 4 parallel pages: 6 to 8 seconds per video in our measurements.

**Alternatives considered but not tried:**

- **Letting the LLM write the whole script, checked only by another LLM.** Rejected early. An LLM judge can miss a wrong number as easily as the writer can make one, and it costs another call per lesson. We use an LLM judge only for whether the question is answered and for clarity. Facts are checked by code.
- **Letting the LLM write animation code directly (for example Manim).** Not tried. Generated drawing code would draw whatever the LLM believes, with no guarantee that it matches the real structure, and it is hard to verify and slow to render.
- **A ready-made AI video service.** Not tried. It would send content to an outside service, could not be verified step by step, and the project needed local export.
- **A cloud text-to-speech service.** Not used. We chose local Piper so that narration runs offline and costs nothing per lesson.

**What we chose.** A structured scene plan that holds operations only, validated with Pydantic, run on real data structures, and verified sentence by sentence. Templates are the fallback, and a coverage gate refuses lessons that do not answer the question. This keeps the LLM's flexibility for understanding the question and writing plain English, while code guarantees every state and number.

### 8.4 Trade-off Analysis

| Trade-off | Decision | Reason |
|---|---|---|
| Accuracy vs creativity | The LLM plans operations only; code computes states; unverified sentences never ship | A wrong video is worse than no video |
| Number of LLM calls vs quality and speed | At most 3 calls per new lesson (plan, one batched repair, one judge) | Each call adds seconds and API load; repairs are batched instead of per scene |
| Free Gemini tier vs reliability | Model fallback list, backoff up to 5 passes, 45 s timeout, 2 calls at once, disk cache, friendly "busy" errors | The free tier is overloaded at times; cached prompts cost nothing |
| Local Piper voice vs voice quality | Local Piper (en_US-lessac-medium) | Free, offline and private; the voice is less natural than paid cloud voices |
| Scene length vs beginner clarity | At most 2 sentences of 25 words per scene; long explanation scenes are split | One idea per scene is easier to follow, at the cost of more scenes |
| Cached lessons vs fresh generation | Cache LLM responses, verified scenes, audio and videos | A repeated question takes about 0.1 s instead of about 10 s; the same question always gives the same lesson |
| Export quality vs export time | Keyframes plus 12 fps during motion, JPEG frames, H.264 veryfast | About 8 s per video; motion is captured at a lower frame rate than real time |
| Supported topics vs honest refusal | Refuse unsupported topics and vague questions with a clear message | A refusal is better than an unrelated or unverified lesson |

### 8.5 Societal and Ethical Impact

**Legal.**

- The lesson text is generated by Gemini and checked by our code. Use of the Gemini API is subject to Google's API terms.
- The Piper package (piper-tts 1.8.0) is licensed GPL-3.0-or-later. The voice model has its own licence, which we must state if the app is distributed.
- Other libraries use permissive licences, for example FastAPI (MIT), google-genai and Playwright (Apache-2.0). ffmpeg was installed separately from the Gyan build.
- We did not copy any existing course video or design.

**Privacy.**

- User accounts store name, email, a bcrypt password hash (cost 12, never the plain password) and the default level. MongoDB also stores the user's saved lessons and quiz results, each linked to the user id.
- Every database query is scoped to the signed-in user, and login attempts are rate-limited.
- Only the question text and lesson content are sent to the Gemini API, never names, emails or passwords.
- The FastAPI backend never sees user accounts.
- Secrets stay in two gitignored files and are not printed or committed.

**Safety.** A wrong explanation misleads a learner. Our mitigations:

- every state comes from real code;
- every number and claim is checked;
- unverified sentences are replaced by code-written ones;
- lessons that do not answer the question are refused with an honest notice;
- unsupported topics are refused, not guessed.

**Fairness and accessibility.**

- Beginner mode is the default and uses everyday words, analogies and short sentences.
- Narration is both spoken and captioned, and the speed can be changed.
- The app is English only, so it does not serve learners who need other languages.
- It covers a limited set of topics.

**Academic integrity and AI-use disclosure.** We used generative AI tools to build the system, as disclosed in Appendix A. The app itself discloses that lessons are generated, and marks verified facts separately from "answers your question".

**Environment and cost.**

- Each new lesson makes at most 3 LLM calls, and cached questions make none.
- Voice, verification, quiz and video run locally, so there is no per-lesson cloud cost for them.
- Local rendering does use the user's CPU.

## 9. Limitations and future work

- **Supported topics.** Arrays (with 2D, static, dynamic and jagged), stacks, queues (with variants), linked lists (with variants), binary search trees, BFS, DFS, bubble sort and insertion sort. Hash tables, heaps, tries, AVL and red-black trees, quicksort, merge sort and Dijkstra are refused.
- **English only.**
- **Depends on the Gemini API** for planning, repair and judging. If it is down, the app shows a busy message; cached questions still work.
- **Visual style.** Whiteboard-style or hand-drawn visuals were not built; the visuals are clean diagram views.
- **Clarity.** One clarity evaluation case still fails, and LLM wording in comparisons can be stilted.
- **Lesson length.** The 30-second minimum is not enforced on every new lesson (one measured lesson was 25.8 seconds).
- **Judge timing.** The judge checks the lesson before repairs; checking again after repairs would need a fourth call.
- **List lessons** use a fixed list of known kinds per structure; kinds outside that list are only explained in words.
- **Video export** needs the frontend running, plus ffmpeg and Chromium installed. Animated moves are captured at about 12 frames per second.
- **Login rate limit** is held in memory, so it resets when the server restarts.
- **Saved lessons and audio.** Saved lessons keep their audio in the backend's local cache. If that folder is deleted, the narration must be generated again.
- **No user study.** The project has not been tested with real beginners yet.
- **Future work:**
  - more structures (hash tables, heaps);
  - more languages;
  - an offline LLM option;
  - a second judge pass after repairs;
  - richer visual styles;
  - user testing.

## 10. Conclusion

Structura shows that an LLM can be used to understand a learner's question and to write plain explanations, while ordinary code guarantees that what is shown and said is true.

The key design choice was to let the model plan only operations, then run them on real data structures and check every sentence. On top of that:

- a coverage gate makes sure the lesson answers the question that was asked;
- a clarity gate makes sure a beginner can follow it;
- local voice and local video export keep the product free to run and private.

In our tests all 256 automated tests pass and all 15 varied questions in the live evaluation pass. The remaining weaknesses, such as one clarity case and some stilted LLM sentences, are listed honestly above.

## 11. Appendix A: AI tool usage and key prompts

**Disclosure.** We used generative AI tools during development:

- Claude Code (Anthropic) as a coding assistant: writing and refactoring code, writing tests, running evaluations and drafting documentation;
- Claude for discussion and review;
- the Gemini API inside the product, for question analysis, narration repair and judging.

All generated code was run, tested and reviewed by the team. The project guide (CLAUDE.md) records the decisions and rules.

**Main prompt themes used to build each module:**

- **Lesson planner.** "Plan a lesson that answers the user's exact question; the LLM outputs operations only, never states; list 3 to 6 answer requirements with their evidence; one scene per answer point." Later: "classify the question's shape (list, compare, why, how, complexity, definition, when, misconception, multipart, data, vague) and validate it in code; list questions must name every item; never fall back to a generic lesson."
- **Verifier.** "Simulate the operations on real structures and check every number and claim in the narration; batch all failing scenes into one repair call with their true states; use code templates as the fallback; templates must always pass."
- **Coverage gate.** "Every lesson must answer the question: deterministic coverage checks, then one judge call at temperature 0 that also rewrites uncovered scenes; if it still fails, show an honest notice."
- **Beginner clarity.** "Make every explanation understandable to a total beginner: at most 2 sentences of about 20 words, picture first and name second, one running analogy, a fixed plain glossary, no jargon before its definition, problem before fix for why questions, no filler words; add a clarity gate and a 12-year-old clarity judge inside the existing judge call."
- **Complexity lessons.** "Answer time-complexity questions with real counted runs, a derivation from the counts, a growth table, and best and worst case, built in code with no LLM call."
- **Revision.** "Fix the fake 'rewritten' revision: compare old and new text, retry once with a stronger instruction, otherwise show an honest message; change only that scene and keep the others byte-identical; show before and after."
- **Video export.** "Export a real MP4 locally with Playwright and ffmpeg, with audio in sync, a quiz slide and caching." Later: "do not capture in real time; capture keyframes, render scenes in parallel, hold frames with the concat demuxer; target under 40% of the video length; prefetch in the background; add cancel."
- **Web app.** "Add Auth.js credentials login, MongoDB with Mongoose, a dashboard with saved lessons and quiz history, and a profile page; fix slow first loads by reusing one MongoDB connection and retrying reads."
- **Reliability.** "Handle Gemini 503 and 429 errors with model fallback, exponential backoff, a timeout and a friendly busy message."
